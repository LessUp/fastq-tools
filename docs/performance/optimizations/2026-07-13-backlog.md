## P0-1：Writer 吞吐优化

| 字段 | 值 |
|------|----|
| 优先级 | P0 |
| 瓶颈来源 | [fastq-io 快照](../benchmark-reports/fastq-io/2026-07-13/summary.md) |
| 现状 | Writer ~420K reads/s，Reader ~10M reads/s，Writer 慢 25x |
| 目标 | Writer 吞吐提升至 ≥2M reads/s（5x 改善） |

### 瓶颈分析

Writer 路径涉及：
- 格式化输出（每条 read 4 行文本）
- 频繁 write 系统调用
- 无批量缓冲

### 优化方向

1. **批量 write**：累积多条 record 到大缓冲区，单次 write 系统调用刷出。减少 user/kernel 切换。
2. **格式化缓冲区复用**：避免每条 record 分配临时字符串。预分配 thread-local 缓冲区。
3. **可选 gzip 流式压缩**：对大输出文件提供 gzip 压缩流（zlib-ng 已是依赖）。

### 验证方式

- 基线快照：[fastq-io/2026-07-13](../benchmark-reports/fastq-io/2026-07-13/summary.md)
- 优化后快照：重跑 `benchmark_fastq_io --benchmark_repetitions=3`
- 对照指标：`BM_FastQWriter_Parameterized/100000` 的 `items_per_second`

### 关联代码

- `src/io/fastq_writer.cpp`
- `include/fqtools/io/fastq_io.h`

## P0-2：batch 初始化 memset 开销

| 字段 | 值 |
|------|----|
| 优先级 | P0 |
| 瓶颈来源 | [callgrind 快照](../benchmark-reports/callgrind/2026-07-13/summary.md) |
| 现状 | stat 路径 memset 占 16.0% Ir，filter 路径占 33.8% Ir；cachegrind 显示 memset 占 76-81% 的 LL 写 miss |
| 目标 | memset 开销降低 ≥50% |

### 瓶颈分析

`FastqBatch` 构造时 `vector::reserve` 预分配大缓冲区，随后 memset 清零。每次 batch 构造都触发：
- `vector<char>` 4 MiB 清零
- `vector<FastqRecord>` 2.13 MiB 清零

### 优化方向

1. **对象池复用**：batch 对象池化，跨命令/跨 batch 复用，避免重复构造 + 清零。
2. **延迟清零**：只在写入位置清零，未写入部分不清零（需保证不读未初始化数据）。
3. **reserve 改 resize 避免重复**：如果 batch 总是写满，用 resize 替代 reserve + 后续清零。

### 验证方式

- 基线快照：[callgrind/2026-07-13](../benchmark-reports/callgrind/2026-07-13/summary.md)
- 优化后快照：重跑 Callgrind，对比 `__memset_avx2` 占比
- 对照指标：`__memset_avx2` 的 Ir 占比从 16-34% 降至 <10%

### 关联代码

- `src/io/fastq_reader.cpp`（`FastqReader::nextBatch`）
- `include/fqtools/io/fastq_io.h`（`FastqBatch` 构造）
- `src/processing/execution_backend.cpp`（batch 生命周期）

## P1-1：batch reserve 策略优化

| 字段 | 值 |
|------|----|
| 优先级 | P1 |
| 瓶颈来源 | [massif 快照](../benchmark-reports/massif/2026-07-13/summary.md) |
| 现状 | 1K reads 数据集峰值 6.23 MiB，batch reserve 按默认 batch_size=10000 预分配，实际只用 1K，浪费 6x 内存 |
| 目标 | 峰值内存降低 ≥60%（1K reads 场景） |

### 瓶颈分析

`FastqBatch::reserve` 按 `batch_size`（默认 10000）预分配，即使输入只有 1000 reads。峰值内存 98.46% 来自 batch reserve。

### 优化方向

1. **按实际 reads 数动态 reserve**：读取文件头/统计行数后按实际规模 reserve。
2. **渐进式扩容**：初始小 reserve，按需扩容（vector 自然增长机制）。
3. **lowMemory profile 验证**：项目已有 `--profile lowMemory`，对比该 profile 下的峰值。

### 验证方式

- 基线快照：[massif/2026-07-13](../benchmark-reports/massif/2026-07-13/summary.md)
- 优化后快照：重跑 Massif，对比峰值
- 对照指标：峰值 useful-heap 从 6.23 MiB 降至 <2.5 MiB（1K reads 场景）

### 关联代码

- `include/fqtools/io/fastq_io.h`（`FastqBatch::reserve`）
- `src/processing/execution_backend.cpp`（batch 构造点）

## P1-2：统计计算 SIMD 向量化

| 字段 | 值 |
|------|----|
| 优先级 | P1 |
| 瓶颈来源 | [callgrind 快照](../benchmark-reports/callgrind/2026-07-13/summary.md) |
| 现状 | `FqStatisticWorker::calculateStats` 占 stat 命令 44.9% Ir，是 stat 核心热点 |
| 目标 | stat 命令吞吐提升 ≥20% |

### 瓶颈分析

统计计算逐 base 处理质量值、长度、碱基组成。当前是标量循环，未利用 SIMD。5800H 支持 AVX2（256-bit），可一次处理 32 个字节。

### 优化方向

1. **质量统计 SIMD**：质量值 0-93，用 AVX2 一次处理 32 个质量值，并行累加 histogram。
2. **碱基组成 SIMD**：A/C/G/T/N 计数用 SIMD 比较指令并行分类。
3. **长度统计**：已有 string_view 长度，无需优化。

### 验证方式

- 基线快照：[callgrind/2026-07-13](../benchmark-reports/callgrind/2026-07-13/summary.md)
- 优化后快照：重跑 Callgrind + Google Benchmark（如有 stat benchmark）
- 对照指标：`calculateStats` 的 Ir 占比从 44.9% 降至 <30%

### 关联代码

- `src/statistics/fq_statistic_worker.cpp`（`calculateStats`）
- `src/statistics/fq_statistic.cpp`（`FastqStatisticCalculator::run`）

### 注意事项

- SIMD 代码需跨架构验证（AVX2 / AVX-512 / NEON）
- 优先用编译器 pragma（`#pragma omp simd`）或 std::simd，避免手写 intrinsics
- 需新增 stat benchmark 目标，当前只有 IO benchmark

## P2-1：大数据集 cache 行为验证

| 字段 | 值 |
|------|----|
| 优先级 | P2 |
| 瓶颈来源 | [cachegrind 快照](../benchmark-reports/cachegrind/2026-07-13/summary.md) |
| 现状 | 1K reads（214 KiB）LL miss rate 0.2-0.4%，无 cache 瓶颈。但数据集远小于 L3（16 MiB） |
| 假设 | 当 batch 累积数据超过 L3（~80K reads × 100bp）时，cache miss 可能上升 |
| 目标 | 确认大 batch 场景是否存在 cache 瓶颈 |

### 验证方向

1. **生成 100K+ reads 数据集**，重跑 Cachegrind，对比 LL miss rate。
2. **调整 batch_size**（1000 / 10000 / 50000），观察 cache miss 变化。
3. **如确认 cache 瓶颈**：考虑 batch 大小自适应（根据 L3 容量 + read 长度计算最优 batch_size）。

### 验证方式

- 基线快照：[cachegrind/2026-07-13](../benchmark-reports/cachegrind/2026-07-13/summary.md)（1K reads）
- 新快照：100K reads Cachegrind，对比 LL miss rate
- 对照指标：LL miss rate 从 0.2% 升至多少？是否超过 5%？

### 关联代码

- `src/io/fastq_reader.cpp`（batch 大小影响 cache 行为）
- `include/fqtools/io/fastq_io.h`（`FastqBatch` 容量）

## P2-2：Reader 大数据集吞吐衰减

| 字段 | 值 |
|------|----|
| 优先级 | P2 |
| 瓶颈来源 | [fastq-io 快照](../benchmark-reports/fastq-io/2026-07-13/summary.md) |
| 现状 | 10K reads 3.67 GB/s vs 100K reads 2.97 GB/s，吞吐降 20% |
| 假设 | 大数据集 cache miss 增加，或 batch 扩容开销累积 |
| 目标 | 大数据集吞吐衰减 <10% |

### 验证方向

1. **中间规模测试**：20K / 50K / 200K reads，绘制吞吐-规模曲线。
2. **batch_size 扫描**：固定 100K reads，batch_size 1000/5000/10000/50000，找最优。
3. **如确认衰减**：考虑预分配策略或 batch_size 自适应。

### 验证方式

- 基线快照：[fastq-io/2026-07-13](../benchmark-reports/fastq-io/2026-07-13/summary.md)
- 新快照：多规模 + 多 batch_size 的 Google Benchmark
- 对照指标：10K vs 100K 吞吐比从 0.81 提升至 >0.90

### 关联代码

- `src/io/fastq_reader.cpp`
- `src/processing/execution_backend.cpp`（batch_size 参数传递）
