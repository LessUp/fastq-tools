# 为什么选择 FastQTools

FastQTools 不是“又一个 FASTQ 小工具集合”，而是把 **FASTQ 质控里最常重复、最容易成为吞吐瓶颈、又最需要可审计结果** 的那一段工作，收敛成一个可解释、可嵌入、可维护的现代 C++ 工具包。

如果你正在评估它是否值得采用，本页先回答三个问题：**它试图解决什么问题、它与常见工具有什么不同、接下来该去哪里验证这些主张。**

## 问题不是“能不能处理 FASTQ”，而是“如何稳定地处理很多 FASTQ”

在真实的测序质控链路里，FASTQ 处理通常并不复杂，但非常高频：

- 上游会持续产出压缩或未压缩的 reads；
- 下游常常要求先做统计、过滤、修剪，再交给比对或组装；
- 数据量一上去，瓶颈往往不是算法本身，而是 **I/O、字符串复制、线程利用率、以及结果是否能复现**。

很多团队真正痛的不是“缺一个命令”，而是下面这些工程问题：

1. **工具链分裂**：统计、过滤、修剪、基准、发布说明分散在不同脚本或不同工具里，结果很难统一解释；
2. **性能不可预测**：同样的 FASTQ，在不同机器、不同参数下吞吐差异很大，但文档没有告诉你数字成立的前提；
3. **集成成本高**：命令行工具很好用，但一旦要嵌入 C++ 程序、放进现有流水线或纳入 CI，就缺少稳定接口；
4. **维护证据不足**：项目说自己“高性能”，但没有把架构选择、benchmark 方法和维护策略串成可审计叙事。

FastQTools 的定位，就是把这段链路做成一个**面向采用决策的技术白皮书型项目**：不是只给你命令，而是把命令、架构、性能证据和维护边界放在同一个阅读框架里。

## FastQTools 的差异化，不在功能数量，而在工程取舍

### 1. 把零拷贝 FASTQ 视图当成一等设计约束

FastQTools 的核心不是“有 `stat` 和 `filter` 两个子命令”，而是 **`FastqBatch` 持有连续缓冲区、`FastqRecord` 通过 `std::string_view` 提供记录视图**。这意味着项目从一开始就在避免解析阶段的无谓复制，把性能讨论落到具体数据模型上，而不是只谈“C++ 很快”。

- 架构说明：[`架构`](../architecture/)
- 深入细节：[`开发者架构设计`](../dev/architecture)
- 相关 ADR：[`RFC-0001: Core Architecture`](https://github.com/LessUp/fastq-tools/blob/master/openspec/baseline/architecture/0001-core-architecture.md)

### 2. 把并行流水线设计成可解释的默认路径

项目明确使用 oneTBB 的 `parallel_pipeline` 组织读取、处理、写回三段式路径，而不是把并发隐藏成黑盒。对采用者来说，这很重要，因为你可以清楚理解：

- 哪一段是串行 I/O；
- 哪一段是可并行的过滤或变换；
- 为什么资源占用应该是有界的，而不是随着文件大小失控。

这类解释会直接影响你是否敢把它放进生产 QC 流程，或者嵌入自己的 C++ 服务中。

### 3. 把“性能主张”变成可追溯证据链

FastQTools 不只是给出一张 benchmark 表，而是把性能证据拆成三层：

- **入口层**：[`性能总览`](../performance/) 告诉你数字应该怎么读；
- **证据层**：[`英文 Benchmark 报告`](../performance/benchmark-report) 提供代表性结果；
- **方法层**：[`Benchmark 指南`](../dev/benchmark-guide) 与 OpenSpec benchmark ADR 解释这些数字如何产生、如何维护。

这种写法的价值在于：你不必盲目相信“很快”，你可以顺着链接判断“这个快，是否和我的工作负载相关”。

### 4. 同时服务 CLI 使用者和库集成者

对很多项目来说，命令行工具与库接口是两套世界。FastQTools 的做法更接近“同一核心、两种入口”：

- 新用户可以从 [`快速开始`](../guide/getting-started) 和 [`CLI 参考`](../guide/cli-reference) 直接上手；
- 需要深度集成的团队可以从 [`API 概览`](../api/overview) 进入 `io`、`processing`、`statistics` 模块；
- 维护者还能继续下钻到 [`核心设计`](../dev/design) 与相关 baseline/ADR。

## 它最适合谁，不适合谁

### 值得重点评估的场景

- 你需要在**预比对质控**阶段稳定完成统计、过滤、修剪；
- 你处理的是**大量 FASTQ 文件或重复批处理任务**，吞吐和资源边界比花哨特性更重要；
- 你希望把 FASTQ 处理能力**嵌入现有 C++ 应用**，而不是永远停留在 shell 脚本层；
- 你在意文档是否能帮助新人快速理解：为什么这样设计、数字从哪里来、风险边界在哪里。

### 不应该误解它的地方

FastQTools 不是：

- 全能型生信流程编排器；
- 替代比对、定量、变异检测等后续工具的“大而全平台”；
- 追求插件生态优先的框架。

它更像是一个**把 FASTQ QC 基础动作做扎实**的工程化内核：范围收敛、证据明确、便于集成。
