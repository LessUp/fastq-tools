# FastQTools GitHub Pages 白皮书级重构设计

> 状态：自主批准（用户要求 autopilot 执行；未等待人工 review）
> 日期：2026-05-17
> 范围：文档站点信息架构、主题系统、图示系统、技术白皮书内容层、参考文献机制

## 目标

把当前 GitHub Pages 重构为面向高级开发者的**技术白皮书站点**，其主叙事严格围绕四个主题展开：

1. **系统架构设计**
2. **算法与执行机制**
3. **技术白皮书与性能证据**
4. **参考资料与演进思考**

站点需要同时具备以下性质：

- 保留 VitePress 的构建效率与 GitHub Pages 兼容性；
- 视觉上具备“工程研究机构 + 极客产品”气质，而不是模板化开源文档站；
- 内容上从“项目说明书”升级为“可供技术选型与架构审查的证据型站点”；
- 在浅色 / 深色模式下保证图示、图标、徽章、卡片、代码块和引导组件都清晰可读。

## 自主假设

由于用户要求先出蓝图再自动实施，且当前无法进行交互确认，本设计采用以下默认假设：

1. **允许激进改版**：现有顶层导航、首页结构、页面分组和视觉风格都可直接替换。
2. **保留双语站点**：`/en/` 与 `/zh/` 继续保留，但共享一套设计系统与信息架构。
3. **不新增后端服务**：所有能力仍以静态站点 + VitePress 运行，不引入外部 CMS。
4. **允许新增轻量站点契约测试**：优先使用 Node 内建能力保护导航、主题与关键页面结构。

## 现状诊断

当前文档站已经有白皮书化倾向，但仍停留在“组件化首页 + 常规文档目录”的阶段，离用户要求的行业标杆仍有明显差距。

### 1. 信息架构仍偏“导航目录”，不够“论证链路”

当前站点主导航聚焦 `Why / Architecture / Workflows / Knowledge Map / Performance / Reference / Resources`。它能路由内容，但尚未建立更强的学术化叙事主轴：

- “算法介绍”缺位；
- “参考文献 / 相关项目研究 / 演进思考”缺位；
- “系统架构 → 算法机制 → 性能证据 → 参考佐证”的完整论证链路尚未形成。

### 2. 首页组件可用，但视觉层次与学术感不够强

当前首页采用多个 Vue 组件拼装，结构清晰，但存在以下问题：

- 首页模块之间更像运营卡片，而不是一页成型的研究型 landing page；
- 视觉基调偏普通文档主题定制，缺少更强的专业感、仪器感、数据感；
- 内容与展示文案直接耦合在组件中，后续大规模升级会增加维护成本。

### 3. 图示系统几乎不存在，现有 SVG 不能满足双主题要求

`docs/assets/images/architecture.svg` 采用固定深色背景与写死颜色值：

- 浅色模式无法自然融入页面；
- 没有 token 化颜色系统；
- 没有复用性，无法扩展成一组统一风格的图示语言。

同时 `docs/assets/images/README.md` 明确表明现有图片资源大多仍是占位思路，不是成熟的品牌资产体系。

### 4. 关键深度内容还不够“可审查”

目前已有架构、性能、参考导航等页面，但缺少高级读者真正关心的“设计证据层”：

- 算法路径如何组织、为什么这样组织；
- 数据结构为何选 `FastqBatch + std::string_view`；
- 并行流水线的阶段边界、资源边界和性能解释；
- 与同类工具或既有方案相比的设计取舍；
- 站在维护视角的“演进路线 / 未来约束 / 不做什么”。

### 5. 学术引用机制缺失

当前页面会引用 OpenSpec RFC、README 或内部页面，但没有形成系统的：

- 参考文献目录；
- 相关开源项目对照；
- 外部论文 / 标准 / 文章引用；
- 页面内统一引用样式。

## 方案比较

### 方案 A：保留现有 IA，仅做视觉升级

**优点**

- 改动范围小；
- 风险最低；
- 很快能得到更“好看”的主页。

**缺点**

- 解决不了内容结构老问题；
- 无法建立“算法 / 引文 / 研究型资料”层；
- 最终只会得到更漂亮的旧站点。

**结论**：不采用。

### 方案 B：在 VitePress 上重建“白皮书型内容操作系统”

核心思路是保留 VitePress 作为静态站点基础设施，但把站点上层完全重构为：

- 新顶层导航；
- 新主页叙事；
- 新的图示组件体系；
- 新的引文与参考资料数据层；
- 新的页面模板与内容模块。

**优点**

- 长期收益最大；
- 技术先进性与维护性兼顾；
- 能以有限工程成本做出显著质变。

**缺点**

- 文档内容与主题组件都要重构；
- 需要重新设计共用数据结构与页面入口。

**结论**：**推荐采用**。

### 方案 C：迁移到全新站点框架

例如完全切换到自定义 Vite + Vue、Astro 或 Next.js 文档站。

**优点**

- 自由度最高；
- 视觉可塑性更强。

**缺点**

- 超出当前任务的必要范围；
- 会把精力从“内容与设计先进性”转移到“框架迁移”；
- 与仓库现有 VitePress 内容体系割裂。

**结论**：不采用。

## 最终设计：Whitepaper OS on VitePress

### 一、站点信息架构

新站点以“理解系统”而不是“浏览目录”为第一原则，顶层导航重构为：

1. **Whitepaper**：项目定位、设计原则、边界与采用判断
2. **Architecture**：系统分层、执行路径、数据模型、资源边界
3. **Algorithms**：过滤、统计、批处理、并行执行模型
4. **Performance**：指标快照、方法学、结果解释、性能证据
5. **Reference**：CLI、API、开发指南、操作手册
6. **Research**：参考文献、相关项目、演进思考、历史材料

相较当前站点：

- `Why FastQTools` 并入 `Whitepaper`；
- `Workflows` 的核心内容折叠进 `Whitepaper` 和 `Reference`；
- `Knowledge Map` 改造成全站级叙事导图，而不是单页概览；
- `Resources` 升级为 `Research`，承载引用、竞品研究与演进材料。

### 二、主题系统与视觉语言

主题不再只是“调色后的 VitePress”，而是完整的**白皮书视觉系统**：

- 颜色：以深墨绿 / 冷青 / 数据蓝为核心，建立高对比语义 token；
- 版式：采用更大留白、窄主栏 + 宽插图区、章节封面式布局；
- 质感：引入网格、渐变、边界高光、研究仪表盘式组件；
- 节奏：首页像技术研究封面，内页像工程设计报告。

具体设计原则：

1. **高信息密度，但不压迫**；
2. **数据元素优先于装饰元素**；
3. **所有卡片、边界、图标和图示都由 token 驱动**；
4. **深浅色模式一开始就视为一等公民，而不是事后补丁**。

### 三、双主题图示系统

关键图示不再依赖固定颜色 SVG，而改为两类实现：

1. **Vue + 内联 SVG 组件**：用于首页核心图、架构总览、流水线图、性能视图；
2. **语义 Mermaid**：仅用于普通流程说明，不承担品牌主视觉。

所有核心 SVG 必须满足：

- 使用 CSS 变量或 `currentColor` 驱动描边、填充、文字；
- 不使用固定深色背景；
- 支持浅 / 深主题自动切换；
- 支持在卡片、正文、全宽区块中复用。

这意味着现有 `architecture.svg` 将被替换成**主题感知型架构图组件**。

### 四、内容数据层

为了避免“文案写死在组件里”的问题，新增面向主题的数据层：

- `siteNavigation.ts`：只负责导航与路由；
- `siteContent.ts`：负责首页叙事块、章节导语、指标摘要；
- `references.ts`：统一维护论文、RFC、文章、开源项目、标准规范；
- `diagrams.ts`：统一维护图示说明、图例、节点标签；
- `timelines.ts`：维护演进思考与版本节点。

这样做的目的不是抽象而抽象，而是为后续以下场景降低成本：

- 中英双语同步；
- 首页和章节页共享同一份指标与引文；
- 页面间复用相同的“证据卡”“引用列表”“演进时间线”。

### 五、页面蓝图

#### 1. 首页

首页升级为真正的白皮书入口页，结构建议为：

1. **Hero / 研究摘要区**：一句话定位 + 三条核心能力 + 直接进入白皮书 / 架构 / 性能
2. **System Snapshot**：系统架构快照图
3. **Algorithm Pillars**：批处理、零拷贝、并行流水线、统计模型
4. **Evidence Overview**：核心 benchmark 与解释边界
5. **Reading Tracks**：评估者 / 集成者 / 贡献者三条阅读路径
6. **Research Rail**：引用、竞品研究、演进页面入口

#### 2. Whitepaper

承载“项目存在的意义与采用判断”：

- 项目定位；
- 问题空间；
- 设计原则；
- 适用边界与不适用边界；
- 采用决策矩阵。

#### 3. Architecture

从系统设计角度解释：

- 分层模型；
- 数据流与控制流；
- `FastqBatch` 与 `FastqRecord` 生命周期；
- `source → processing → sink` 执行链；
- bounded resource 约束。

#### 4. Algorithms

这是本次重构新增的重点层，至少包含：

- **Filtering model**：谓词组合与短路策略；
- **Statistics model**：统计路径、指标粒度、结果构建；
- **Execution model**：oneTBB 并行流水线与阶段分工；
- **Memory model**：零拷贝视图、批对象复用、缓存 / 分配策略。

#### 5. Performance

保留 benchmark 内容，但重构表达方式：

- 结论快照；
- 方法学；
- 结果解读；
- 架构解释；
- 复现实验入口；
- 常见误读澄清。

#### 6. Research

这是站点学术感的关键层，新增三类页面：

- **Bibliography**：统一参考文献与说明；
- **Related Projects**：与 fastp、seqtk、fastqc 等项目的维度化对照；
- **Evolution Notes**：记录当前设计如何演进、哪些方向刻意不做。

### 六、引用机制设计

新增统一引用目录与组件：

- `ReferenceList.vue`：渲染按类别分组的参考资料；
- `ReferenceBadge.vue`：在正文中标记 RFC / paper / repo / article 类型；
- `EvidenceCallout.vue`：将“性能数字 + 引用来源 + 方法学入口”组合成证据块。

引用数据最少包含：

- `id`
- `title`
- `authorsOrOrg`
- `year`
- `type`
- `href`
- `annotation`
- `localeNote`

这让页面可以做到接近论文式表达：正文中做轻量引用，页尾或研究页集中列出来源。

### 七、深浅色模式修复策略

本次不做“局部修补”，而是整体升级：

1. 统一主题 token，禁止在核心组件内硬编码深浅主题颜色；
2. 所有图示改为变量驱动；
3. 链接、徽章、边框、网格、阴影和代码块都走语义变量；
4. 对高亮数字卡、引用标签、图例文本设置最小对比度目标；
5. 对 GitHub badge、外链图标、社交图卡等资源进行亮暗模式兼容处理。

### 八、实现分层

本次实施建议拆成四个工程流：

1. **Theme Foundation**：token、布局、导航、主题组件基座
2. **Homepage & Diagram System**：首页重做、架构图与证据图组件
3. **Content Restructure**：新增 / 重写 Whitepaper、Algorithms、Research 页面并调整目录
4. **Validation & Publishing**：文档构建、契约测试、changelog、最终推送

### 九、验证策略

除 `cd docs && npm run build` 外，新增轻量文档契约验证：

- 首页必须出现核心章节入口；
- Research 层必须包含 bibliography / related projects / evolution；
- 主题 token 文件必须同时定义 light / dark 变量；
- 核心图示组件不得引用固定深色背景 SVG；
- 导航和侧栏必须覆盖新的顶层信息架构。

优先使用 Node 内建测试能力，不新增额外测试框架。

## 非目标

本次重构明确不做：

- 替换 VitePress；
- 把所有现有 reference 手册重写成长篇白皮书；
- 对项目产品功能做超出基线的新承诺；
- 为了视觉效果引入重型前端依赖。

## 验收标准

当以下条件同时满足时，本次重构可视为完成：

1. 首页、顶层导航、章节入口均切换到新 IA；
2. 至少形成一套主题感知型核心图示；
3. `Algorithms` 与 `Research` 两个新增层级落地；
4. 深浅色模式下图示与关键视觉元素清晰可读；
5. 中英文首页与新增核心章节保持结构一致；
6. GitHub Pages 可本地成功构建；
7. 本次变更写入 `changelog/`。
